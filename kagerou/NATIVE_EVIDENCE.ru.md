# Kagerou: основания по исходной программе

[中文](NATIVE_EVIDENCE.zh.md) | [English](NATIVE_EVIDENCE.en.md) | [Русский](NATIVE_EVIDENCE.ru.md) | [日本語](NATIVE_EVIDENCE.ja.md)

[Каталог документации](../docs/README.ru.md)

Справочник для разработки адаптера бонусного издания: идентификация EXE, команды и геометрия интерфейса. Эти образцы не устанавливают поведение других версий движка.

Запись: 2026-10-10; обновление бонусных ресурсов: 2026-10-11. Это статический анализ, не запуск исходной игры. Адреса — VA при базе `0x400000`, не смещения файла. Читатель реализован независимо в этом каталоге, без импорта семантики команд из других адаптеров.

## Версии входных данных

| Файл | SHA-256 |
| --- | --- |
| Исходный `kagerou.exe` | `f02998fae350945f4de4dc7eab47997e1e2d9b8aa43d49740a80aad893dcde9b` |
| Китайский `kagerou_gbk.exe` | `0d024e5cfe6c70f5a9a9149df5fbf040dfb7d97cdeefba03a13625d121dea8de` |

Оба — i386 PE32. В `.text` меняются только `0x80 → 0x86` по адресам `0x456d4a`, `0x45d0f3`: аргументы кодировки двух путей создания шрифта. В других секциях есть локализованные данные; весь EXE не является двухбайтовой правкой.

Первоначально проверены 147 исходных / 140 переведённых сцен. Поддерживаемое бонусное издание содержит162 сцены:98 `modern`,64 `rscript19`. Пересобранный перевод содержит155 сцен, ещё7 используют японский оригинал. Контейнер `modern-36` не доказывает одинаковую схему opcode. Старые наборы содержали по861 `excmd`; новый оригинал —936, режимы `0:590 / 1:263 / 2:83`.

## Диспетчер

Главный интерпретатор `0x41bd00`. Для не-VM команд `0x41c12f` берёт младшие16 бит, вычитает3 и использует байтовый индекс `0x41d4f8` и таблицу обработчиков `0x41d2e8`. `native.py` читает их непосредственно: таблица opcode из репозитория не заменяет бинарное доказательство.

| Opcode | Обработчик | Прослеженный вызов |
| --- | --- | --- |
| `0x14` | `0x41c5e9` | Два выражения → `0x41f250` (`gload`) |
| `0x1a` | `0x41cad3` | `0x41ff10` (`queue`) |
| `0x1c` | `0x41cae7` | Три выражения → `0x41ff40` (`update`) |
| `0x51` | `0x41c9ae` | `0x41f020` (`TXT`) |
| `0x52` | `0x41ca0b` | `0x41eeb0` (`TXA`) |
| `0xff` | `0x41d29d` | Пять выражений → `0x421f00 → 0x431320` |

TXT читает выражение, сырой DWORD, два выражения, две сырые строки и последнее выражение. Первая строка отбрасывается, вторая сохраняется, последнее выражение ограничивается младшими16 битами. Не все последующие правила текста, голоса и ожидания прослежены: это описание чтения/вызовов, не полная реализация TXT.

## Модель EXCMD

`0x431320` выбирает режим по младшим16 битам; кроме0/1/2 сразу возвращается. Пятый аргумент здесь не используется. Модель принимает пять уже вычисленных беззнаковых WORD, а не вычисляет выражения.

### Режим 0: загрузка и необязательный фокус

`0x431370` принимает слоты1–7. Выбирает X по настройкам, вызывает `0x41dda0(slot,cg,0,x,0,0)`, при нулевом четвёртом аргументе — `0x431440(slot)`, затем при нуле `0x482188` — обновление `0x41dd30`. Фокус тоже проверяет обновление: вне очереди возможны два вызова. Нельзя игнорировать четвёртый аргумент или превращать очередь в немедленное обновление.

Выбор X в `0x431385–0x4313cc`:

```text
WORD[0x482a6a] != 0:
    signed WORD[0x47eede + 2 * slot]
иначе:
    signed WORD[0x47eeba + 2 * (6 * (WORD[0x482a66] / 3) + slot)]
```

Деление неотрицательного WORD целочисленное. Для слотов1–6:

| Явная настройка | X |
| --- | --- |
| layout=0, alternate=false | 200, 200, 300, 400, 500, 600 |
| layout=6, alternate=false | 600, 600, 500, 400, 300, 200 |
| alternate=true | 400, 200, 300, 400, 500, 600 |

Это ветви, не доказанные значения по умолчанию. Слот7 допустим, но фокус обрабатывает только1–6; заменять7 на6 нельзя.

### Режим 1: очистка

`0x431410` вызывает `0x41e020(slot,0)` и обновляет по состоянию очереди. Два условных перехода не исключают ни одного WORD; ограничение slot<100 проверяет следующий уровень `0x41dd70`. Слот0 передаётся без преобразования: EXCMD не реализует «очистить все портреты».

### Режим 2: фокус и цвет

`0x431440` записывает r20 и обходит слои1–6:

| Слой | `0x41f940(layer,depth)` | `0x41f7f0(layer,mode,strength)` |
| --- | --- | --- |
| Выбранный | depth=8 | mode=0, strength=0 |
| Другой, `WORD[0x482a6c]==0` | depth=номер слоя | mode=4, strength=50 |
| Другой, `WORD[0x482a6c]!=0` | depth=номер слоя | mode=0, strength=0 |

Два `push esi` в `0x431478` подтверждают глубину по номеру слоя, не1. `0x41f940 → 0x41e360` задаёт глубину. `0x41f7f0 → 0x41e2d0 → 0x4058b0 → 0x408e40` меняет параметры рисования. Таблицы `0x408f40/0x408f24` направляют режим4 в `0x408ea6`, внутренний режим **3**, сила `50*255/100=127`. Виртуальные методы `+0xb0/+0xb4` таблицы `0x473f7c` — `0x43fa30/0x43fb00`, поля режима `+0x28` и силы `+0x2c`.

Рисование `0x4406e0 → 0x4412c4/0x44125c → 0x440e65` использует `0x444380` для прозрачного контура и `0x444220` для другой ветви. RGB проходит LUT `0x4a732c` перед записью/смешением: это не общая прозрачность и не серый цвет. Инициализация `0x446079..0x4460ed` использует `0x475c38=256.0`, `0x475c50=1/256` и усечение `0x4616b0`:

```text
L(level,channel) = trunc(channel*(256-level)/256)
output = L(a,L(level,source)) + L(255-a,destination)
```

a — обратная альфа четвёртого байта. При127 коэффициент **129/256**, не50% и не128/255. Общий dim256 реализует только RGB LUT; адаптер преобразует `(4,50)` в `("dim256",127)`, не меняя числовые draw других игр. Ren'Py сохраняет покрытие PNG и смешение GPU; округление краёв не побайтовое. Изолированные GL2 проверки прозрачных/полупрозрачных/непрозрачных пикселей и сил0/127/255 допускают2 уровня расхождения.

## Видео

Оконная функция `0x4233c0`: сообщение `0x40e` использует `0x47ecf8`, `.\\mov\\0002.mpg`; `0x41e` — `0x47ece8`, `.\\mov\\0001.mpg`, затем задаёт состояние запуска. Есть только0002/0003. movie3 встречается в финалах1131/1239/1326/1417/1418.

Пользователь разрешил общий запуск: существующие0002, затем0001 только при открытии приложения; отсутствующий0001 вызывает предупреждение. Сценарные вызовы сохраняются. В game/script.rpy флаг renpy.session предотвращает повтор при возврате к заголовку и full_restart того же процесса.

## Вызовы 0999 → 1000

База —162 бонусные сцены; хеш EXE прежний. Добавлены0059/0201/0301/0302/1501..1511. В0001 jump201 открывает CG, jump301 — сцены;0302 через gosub вызывает именованный вход "scmode". Старый китайский поток команд нельзя подставлять целиком: пересборка TXT сохраняет новые команды и конечную таблицу входов. Это данные TSC, не ручная проверка всех галерей/разблокировок.

### Выбор изображений не требует setlink

`setclk: 0x41cb59 → 0x41ffa0 → 0x41e800 → 0x405cb0` записывает разрешение клика, результат и наведение в объект+298 без требования setlink (необязательная картинка пояснения). `0099%select` законно задаёт только setclk для21–24. Нельзя отсеивать объекты без link или пропускать выбор.

После _gosub999 скрипт0050 передаёт1000 первым аргументом _insub локальному входу; тот выполняет _gosub _r[10]0... Старый runtime записывал r10–19 до вычисления цели, заменяя1000 нулём и вызывая _0000. Исправление: вычислить цель и все аргументы до записи регистров, не менять сценарий.

- Opcode15: `0x41d820` читает цель и10 параметров во временные WORD, вызывает `0x41da10`; `0x41da7a → 0x41d930` загружает цель; `0x41dabe..0x41dad3` затем записывает параметры.
- Opcode200: `0x41c427` читает локальный DWORD-адрес, `0x41c43d..0x41c449` — параметры, затем `0x41daf0`.
- Opcode16: `0x41c481..0x41c487 → 0x41db80` восстанавливает сценарий/курсор вызывающего; `0x41dbf9` записывает r0. return0 в0999 корректен.

## Текст и начала координат

- `0x41f0e1` при `WORD[0x482ae0]==1` очищает через `0x41ee80`. tclsmode `0x4206d0` меняет WORD; старт задаёт2.
- `0x42d81a` при существующем тексте и ненулевом ожидании добавляет ^n из `0x47ee88`. `0x42d86c` для начала CP932【 по `0x47ee94` добавляет U+3000,^n из `0x47ee80`. TXT не просто склеивает абзацы.
- `0x42d8d1 → 0x430db0` добавляет; при отказе `0x42d8da → 0x430f30` очищает и повторяет текущий абзац. Ren'Py проверяет реальную высоту вёрстки, не исходную байтовую ёмкость. Разбиение внутри абзаца не завершено.
- `WORD[0x482a5e]`:0 вертикально,1 горизонтально (прежняя трактовка иконок была обратной). SETE `0x430437`:0 ведёт к `0x453ef0`, полю `+0x1b0=1`, `0x455400 → 0x455800`: Y растёт, столбцы справа налево.1 использует `0x455420`: X растёт, строки вниз. Порт сохраняет1=вертикально/0=горизонтально, преобразуя таблицы/кнопки. Вертикальное значение по умолчанию подтверждено пользователем; `0x419bb0` обнуляет BSS нового CFG, поэтому статический EXE не доказывает байт направления1. Native CFG не импортируется.

Предустановки `0x43027f..0x43042b`; `0x453eb0` пишет физические размеры в `+0x170/+0x16c`, не транспонированные:

| Направление | Индекс | Шрифт | Область | Интервал | Ruby |
| --- | --- | --- | --- | --- | --- |
| Вертикально | 0 | 24 | 646×480 | 10 | 9 |
| Вертикально | 1 | 18 | 494×360 | 8 | 8 |
| Вертикально | 2 | 12 | 342×240 | 6 | 6 |
| Горизонтально | 0 | 18 | 360×513 | 9 | 9 |
| Горизонтально | 1 | 16 | 320×456 | 8 | 8 |
| Горизонтально | 2 | 12 | 240×342 | 6 | 6 |

Константы не доказывают визуальное равенство. По просьбе пользователя порт использует24/18/12px в обоих направлениях; меняются геометрия и направление глифов, исходные области/начала/интервалы сохраняются. Большая вертикальная область646×480, не горизонтальная360×513.

- `0x43045c..0x430788`: чередующиеся X/Y по индексу snap+54*direction+18*size (исходное направление). Все54 комбинации в native.py: вертикально0/0=(114,30), горизонтально0/0=(400,20), вертикально2/8=(20,270). Ren'Py использует правый верхний якорь(x+width,y), перенос по физической высоте. TextSegment SDK не наследует направление: нужны HarfBuzz/вертикальные формы, иначе CJK повёрнут. Изолированные снимки проверяют прямые глифы и переключение.
- tbox `0x41c8cb → 0x41f220` выбирает `0x41e550/0x41e570` вторым аргументом, затем условное обновление. Скрытие `0x42da47` вызывает очистку `0x42d9d0`.0999 заканчивается tbox0 0 без txcls: скрытие должно очищать буфер. txcls: `0x41ca48 → 0x41ecd0 → 0x41e590`.
- locmode `0x41c801 → 0x41f890` читает4 выражения, слой0 обходит1..99. `0x41e310 → 0x405740` пишет начала координат. Ненулевое четвёртое поле не восстановлено, образцы используют0. `0x408569..0x4085d5` вычитает целую половину ширины/высоты при ненулевых первых полях, подтверждая центрирование. Полупиксельные края требуют сравнения.
- endscene `0x41cb25` проверяет WORD повтора `0x4821f8`: обычный сценарий продолжается, ненулевой завершает интерпретатор. Флаг по умолчанию false; при этой записи ещё не было исходного входа галереи.

Общий runtime предоставляет регистры, медиа и контролы, не копирует специальные переопределения других игр. Общие переходы совместимые; миллисекунды описаны ниже, точные пиксели не сравнены.

## Синтаксис и положение ruby

Проверен оригинальный EXE указанного хеша, не чужой порт. Другой шрифт не гарантирует растеризацию GDI.

- `4544d9..4544e6 → 45f150`: | сохраняет номер текущего основного элемента в +7c и флаг+78; не отображается.
- `4544ff..45459d` копирует чтение из [...] и завершает базу на текущем индексе−1, вызывает45f170. Без | функция `45f18b..45f197` задаёт начало равным концу. 躯[み]/介[お] — ruby одного знака. В1000.tsc есть оба варианта; 抉[えぐ]/熾[おこ] в1000.rpy:29 ошибочно показывались как основной текст на снимке пользователя.
-45ead0 выбирает горизонтальное45eb20/вертикальное45ed60 и обнаруживает новую строку/столбец по возврату X/Y. Через границу выделяется ceil(остаток чтений*текущие базовые знаки/остаток базовых знаков), рекурсивно `45eb9d..45ebde` / `45eddd..45ee1e`.
- Горизонтально `45ec75..45ed3f`: короткое чтение центрируется в равных ячейках базы; длинное — целиком с реальными ширинами. Y=верх базовой ячейки−смещение+74, не догадка по ascender.
- Вертикально `45eeb3..45efa8`: аналогично по высоте; правый край чтения=правый край первой базы+смещение+74, направление вниз. Транспонированный Ren'Py использует тот же верх−смещение, без дополнительной высоты шрифта.
- `4303cb..43042b` задаёт размер+68 и смещение+74 равными9/8/6; это явные настройки, не предположение по году игры.

Тесты охватывают обе формы, переносы, распределение чтений, смещения и направление SDK. Снимки используют начало1000, не сохранения игрока. Основания Kagerou не унифицируют ruby других EXE; геометрия Forest/Khime сохранена.

## Ожидание и бонусные галереи

- `0x430cb0..0x430d39`: таблица[24,18,12,18,16,12], индекс3*direction+size выбирает grps/waitNN, не body/grow. Четыре LWG по60 кадров, порядок и начала из .meta.xml.
- `0x4191a9` задаёт указатель `0x47e588`; WORD+0x190=50. `0x4192b1 → 0x44fc90 → 0x44fca0` ставит таймер50ms; `0x44b980` увеличивает кадр, `0x44b9ab` возвращает0. Это не свечение body/grow.
- `0x430dfc → 0x430f60 → 0x455b30` получает ячейку последнего знака. `0x430e01`: вертикально wait слева снизу, горизонтально справа сверху, не в углу экрана. Порт берёт ячейки Ren'Py без ruby.
- У 『「【 вертикальный HarfBuzz-контур может выйти за advance. Общий слой вписывает допустимый bearing в ячейку без изменения полноширинного шага/интервала; реальные границы SDK24/18/12px проверены.
- folder `0x41cee0 → 0x41fb80`, слой0: цикл1..99 в `0x41fbb1..0x41fbc8`. Для0201/0301 folder0 grpo_ex и locmode0 0 0 0 должны действовать вместе: миниатюры не наследуют центр портретов. Общая механика Forest/Khime использована на основании этого EXE; бонусные TSC по-прежнему управляют галереями.

Проверки2026-10-11: константы EXE,162 TSC только для чтения, изолированные SDK-регрессии очистки/каталога/начала/шрифта/границ и снимки обоих направлений. Lint сохраняет предупреждения японских имён и недостижимых строк. Полные маршруты/Android не проверены.

## Панели чтения

### Утечка каталога портретов бонусного издания (2026-10-11)

0001 задаёт всем объектам grpo; галереи —grpo_ex/левый верх. Путь0050→0999→1000 не повторяет grpo_bu/центрирование слотов1..6 из0000. EXCMD запрашивает отсутствующий grpo/3011; прозрачная заглушка скрывает портреты всю игру. Ресурсы присутствуют, это не пропуск копирования.

Порт при загрузке EXCMD1..6 восстанавливает каталог/начала, явно объявленные0000/9999, не меняя folder-all, миниатюры и слот7. EXE `431370 → 41dda0 → 405940` использует текущий каталог; автоматический сброс старого EXE после бонусного заголовка не доказан. Это коррекция порта по текущим сценариям/ресурсам. Японские/китайские изолированные тесты идут от реального выбора заголовка через0050/0999 до первого портрета1000, без сохранений игрока.

`0x42c2be..0x42c2d6` размещает compane(585,572), `0x42bfce..0x42bfe3` —excompane(0,550). Изображения/размеры/начала из метаданных; excompane без фона. Названия подтверждены указателями строк конструктора, не порядком памяти.

## update: миллисекунды (2026-10-11)

`0x41cae7 → 0x41ff40 → 0x41e5b0` читает эффект/шаги/ожидание; `0x41e5cc..0x41e5d1` заменяет0 шагов на10. Таблица `0x41e7e0`: сразу, растворение, упорядоченная замена, белый, чёрный.

| Эффект | Цикл | Номинальные секунды |
| --- | --- | --- |
| 1 | `0x450630`, `0x4506c5`:шаги+1 | (step+1)*wait/1000 |
| 2 | `0x4504e0`, `0x450540`:шаги−1, неположительное пропускается; не мозаика | max(0,step-1)*wait/1000 |
| 3 / 4 | `0x450f50 / 0x450cb0`, две фазы по шаги+1 | 2*(step+1)*wait/1000 |
| Маска | `0x450380`, удвоить шаги, затем−1 | (2*step-1)*wait/1000 |
| 1xx / 2xx | `0x4507a0 / 0x450940`, две фиксированные петли31/41 кадров Sleep(5) | 0.310 / 0.410 |

WINMM!timeGetTime (IAT `0x4732dc`) и минимум один KERNEL32!Sleep(5) (IAT `0x473070`) за цикл до разницы **больше** wait. codex-ms считает номинальные циклы, не планировщик Windows. Тогда эффект2 ещё был пикселизацией, исправленной ниже. В текущем японском корпусе константы0..3:1 32 40=1.32s;1 16 20=.34s;0999:1 15 100=1.60s против прежних12.8/3.2/15. Kagerou явно выбирает миллисекунды; другие порты при этом получили только общую правку времени эффекта2. Нулевые шаги заменяются10 до конструктора, устраняя деление на0. Байтовые проверки EXE/SDK охватывают длительности, регистры/очередь, не точные пиксели/планирование.

## update 2: упорядоченная замена (2026-10-11)

`0x45050a` задаёт режим **18**, не масштабирование. `0x4412c4[18] → 0x44125c[13] → 0x440c17`; непрозрачная ветвь `0x440c33 → 0x4437d0`. `0x443855..0x44385b` сдвигает силу на4, выбирает16 WORD по `0x47ef38`. `0x443899..0x4438ef` проверяет бит(x%4)+4*(y%4):1 новый пиксель,0 старый. `0x45e01a..0x45e01c` делает высоту DIB отрицательной, подтверждая строки сверху вниз.

# KagerouTouryuuki 原生证据

记录日期：2026-10-10；特典版资源更新：2026-10-11。以下为静态分析，不是原游戏运行结果。
地址是加载基址 `0x400000` 下的 VA，不是文件偏移。
读取工具独立实现于本目录，不从其他适配器导入指令语义。

## 输入版本

| 文件 | SHA-256 |
| --- | --- |
| 原版 `kagerou.exe` | `f02998fae350945f4de4dc7eab47997e1e2d9b8aa43d49740a80aad893dcde9b` |
| 中文补丁 `kagerou_gbk.exe` | `0d024e5cfe6c70f5a9a9149df5fbf040dfb7d97cdeefba03a13625d121dea8de` |

两者均为 i386 PE32。补丁 `.text` 的差异仅为 `0x456d4a`、`0x45d0f3`
处的 `0x80 → 0x86`，对应两条字体创建路径的字符集参数。
其他节仍有本地化数据差异，不能称为“整个 EXE 只改了两个字节”。

初次审计的旧资源为 147 原版／140 补丁场景。
当前支持的特典版原版 TSC：162 场景，98 个 `modern`、64 个 `rscript19`；
重建后的补丁为 155 场景，另 7 个未翻译场景回退原版。
全部标注 `modern-36`，不据此推定 opcode schema 相同。
旧版各有 861 条 `excmd`。当前特典版原版有 936 条，
模式计数为 `0:590 / 1:263 / 2:83`。

## 指令分派

主解释器 `0x41bd00`。非 VM 指令在 `0x41c12f` 取低 16 位，减 3，
通过 `0x41d4f8` 的字节索引表和 `0x41d2e8` 的处理函数表跳转。
`native.py` 直接读取这两个表，不把既有仓库 opcode 表当作二进制证明。

| Opcode | 分派地址 | 已追踪的调用 |
| --- | --- | --- |
| `0x14` | `0x41c5e9` | 两个表达式 → `0x41f250`（`gload` 路径） |
| `0x1a` | `0x41cad3` | `0x41ff10`（`queue` 路径） |
| `0x1c` | `0x41cae7` | 三个表达式 → `0x41ff40`（`update` 路径） |
| `0x51` | `0x41c9ae` | `0x41f020`（`TXT` 路径） |
| `0x52` | `0x41ca0b` | `0x41eeb0`（`TXA` 路径） |
| `0xff` | `0x41d29d` | 五个表达式 → `0x421f00` → `0x431320` |

`TXT` 路径读取一个表达式、一个原始 DWORD、两个表达式、两个原始字符串，
以及最后一个表达式。它丢弃第一个字符串，保留第二个字符串，并取最后
表达式的低 16 位。后续文字布局、语音和等待的全部语义尚未完成追踪；
此处只确认读取与调用路径，不宣称实现了完整 `TXT`。

## EXCMD 调用模型

`0x431320` 按模式的低 16 位分派。模式 0、1、2 之外直接返回，
第五个参数在这条调用路径中未使用。
模型当前只接受五个已解析的无符号 WORD；表达式求值不属于该模型。

### 模式 0：加载并可选切换焦点

`0x431370` 接受槽位 1～7，其他槽位直接返回：

1. 读取配置，选取 X 坐标。
2. 调用 `0x41dda0(slot, cg, 0, x, 0, 0)`。
3. 第四个参数为 0 时调用焦点函数 `0x431440(slot)`。
4. `0x482188` 为 0 时调用 `0x41dd30` 刷新。

焦点函数也检查刷新条件，因此非队列加载且切换焦点时会出现两次刷新调用。
不能为了简化而将其改成队列中立即刷新，或忽略第四个参数。

X 坐标读取表达式由 `0x431385–0x4313cc` 确认：

```text
WORD[0x482a6a] != 0:
    signed WORD[0x47eede + 2 * slot]
否则:
    signed WORD[0x47eeba + 2 * (6 * (WORD[0x482a66] / 3) + slot)]
```

非负 WORD 除法取整数部分。槽位 1～6 的抽取结果：

| 显式配置 | X 坐标 |
| --- | --- |
| layout=0，alternate=false | 200, 200, 300, 400, 500, 600 |
| layout=6，alternate=false | 600, 600, 500, 400, 300, 200 |
| alternate=true | 400, 200, 300, 400, 500, 600 |

这里只列举配置分支，不确认哪组为默认值。槽位 7 虽通过原生检查，
焦点循环仍只处理 1～6；不擅自将其规范化为 6。

### 模式 1：清除

`0x431410` 调用 `0x41e020(slot, 0)`，并按队列状态刷新。
它的两次条件跳转实际上没有排除任何 WORD 值；槽位合法性由下一层
`0x41dd70` 检查（小于 100）。槽位 0 原样传入清除函数，
**不是由 EXCMD 实现的“清除全部立绘”**。

### 模式 2：焦点

`0x431440` 写入寄存器 20，并循环图层 1～6：

| 图层 | `0x41f940(layer, depth)` | `0x41f7f0(layer, mode, strength)` |
| --- | --- | --- |
| 与指定槽位相同 | depth=8 | mode=0, strength=0 |
| 其他，`WORD[0x482a6c] == 0` | depth=图层编号 | mode=4, strength=50 |
| 其他，`WORD[0x482a6c] != 0` | depth=图层编号 | mode=0, strength=0 |

其他图层的深度来自 `0x431478` 的两次 `push esi`，不是统一深度 1。
`0x41f940 → 0x41e360` 写图层深度；
`0x41f7f0 → 0x41e2d0 → 0x4058b0 → 0x408e40` 修改图像绘制参数。
绘制模式 4 通过 `0x408f40/0x408f24` 两级表到 `0x408ea6`，
调用图像内部模式 **3**；强度 50 转为整数 `50 * 255 / 100 = 127`。
内部模式 3 的像素算法尚未确认，不能仅凭数字称为灰化、透明或变暗。

## 视频

窗口消息路径 `0x4233c0`：`0x40e` 使用 `0x47ecf8` 的
`.\\mov\\0002.mpg`；`0x41e` 使用 `0x47ece8` 的 `.\\mov\\0001.mpg`，
然后设置启动状态。当前资源只有 `0002.mpg`、`0003.mpg`。
`movie 3` 出现在 `1131/1239/1326/1417/1418` 五个结局场景。

用户已允许沿用既有启动流程。后续仅在打开程序时按 0002、0001 的顺序
播放存在的视频，缺失 0001 发出警告；保留剧本自身的视频调用。
生成器覆盖层 `game/script.rpy` 已接入，`renpy.session` 标志保证同进程
返回标题或 `full_restart` 不重复播放启动视频。

## 0999 → 1000 的调用顺序

资源基准现为安装「ハチポチ特典」后的 162 场景；EXE 哈希未改变。
新增 `0059/0201/0301/0302/1501..1511`，标题 `0001` 的入口与旧版不同。
当前 `0001` 通过 `jump 201` 进入 CG 鉴赏、`jump 301` 进入场景鉴赏，
`0302` 以 `gosub ... "scmode"` 调用新版剧情的命名入口。
因此不能用旧中文整段指令覆盖这些场景；TXT 重建保留新版指令及尾部入口表。
上述是当前 TSC 的调用证据，不证明完整鉴赏或解锁效果已人工验证。

### 图片选项不要求 setlink

`setclk` 的 `0x41cb59 → 0x41ffa0 → 0x41e800 → 0x405cb0` 写入已加载对象
`+298` 的点击启用、返回值与悬停模式；不检查 setlink。后者是可选的悬停说明图。
`0099%select` 只对 21～24 设置 setclk，不提供 setlink，这是合法路径。
适配启用已加载图片命中区域，不能过滤无 link 的对象或绕过选择直接返回。

`0050` 在 `_gosub 999` 返回后，将 1000 作为 `_insub` 的首个参数传入本地入口。
该入口执行 `_gosub _r[10] 0 ...`，并不是在 0999 末尾直接跳转。
旧共享运行时先写参数寄存器 10～19，再解析调用目标，导致 1000 被 0 覆盖，
调用 `_0000`。修复为先求值目标及全部参数，再写寄存器；不修改游戏脚本。

- opcode 15 经 `0x41d820` 读取目标及十个参数到临时 WORD 数组，再调用
  `0x41da10`；`0x41da7a → 0x41d930` 加载目标，`0x41dabe..0x41dad3`
  随后写入参数寄存器。
- opcode 200 在 `0x41c427` 读取本地 DWORD 地址，`0x41c43d..0x41c449`
  读取参数，再调用 `0x41daf0`。
- opcode 16 经 `0x41c481..0x41c487 → 0x41db80` 返回，恢复调用者脚本/游标，
  `0x41dbf9` 设置寄存器 0。0999 末尾的 return 0 本身没有错误。

## 文字与原点（生成器预设）

- `0x41f0e1` 检查 `WORD[0x482ae0] == 1`，为真先调用 `0x41ee80` 清页；
  `tclsmode` 的 `0x4206d0` 写此 WORD。启动脚本明确设置为 2。
- `0x42d81a` 在已有文字、等待非零时先追加 `0x47ee88` 的 `^n`；
  `0x42d86c` 在正文以 `0x47ee94` 的 CP932 `【` 开头时额外追加
  `0x47ee80` 的 `U+3000,^n`。普通 TXT 不是直接拼到上一段末尾。
- `0x42d8d1` 调用 `0x430db0` 追加，失败时 `0x42d8da` 调用
  `0x430f30` 清页，再追加当前段落。Ren'Py 用实际字形布局高度检查溢出；
  不是字节级原生容纳判定，单段分页仍未实现。
- `WORD[0x482a5e]` 为方向：0 竖排、1 横排。先前按图标外观解释反了。
  `0x430437` 是 SETE：原生 WORD=0 时 `0x453ef0` 写 `+0x1b0=1`，
  `0x455400` 分派到 `0x455800`，按字高累加 Y、从区域右边向左推进列。
  WORD=1 则走 `0x455420`，按字宽累加 X、向下推进行。
  端口设置仍保持 1=竖排、0=横排，读取原生表和方向按钮时反向映射。
  按用户确认，端口默认竖排；`0x419bb0` 的新 CFG 初始化会清零这些 BSS 字段，
  因此不能据 EXE 静态文件宣称默认方向字节就是 1。端口不导入已有原生 CFG。
- `0x43027f..0x43042b` 的预设如下。`0x453eb0` 的两维参数写入字段
  `+0x170/+0x16c`，下表竖排区域是物理宽×高，不是转置后的虚拟布局尺寸。

| 方向 | 字号档 | 字号 | 物理区域 | 行/列距 | ruby |
| --- | --- | --- | --- | --- | --- |
| 竖排 | 0 | 24 | 646×480 | 10 | 9 |
| 竖排 | 1 | 18 | 494×360 | 8 | 8 |
| 竖排 | 2 | 12 | 342×240 | 6 | 6 |
| 横排 | 0 | 18 | 360×513 | 9 | 9 |
| 横排 | 1 | 16 | 320×456 | 8 | 8 |
| 横排 | 2 | 12 | 240×342 | 6 | 6 |

上述字号是原生调用常量，不是像素视觉等价的证明。按用户反馈，端口显示字号
统一为 24/18/12px，方向切换只改变几何和字形方向。原生区域、原点与
行/列距仍保留；竖排大字恢复为 646×480，不再误用 360×513 的横排区域。

- `0x43045c..0x430788` 的立即数栈表按 `snap + 54*direction + 18*size`
  索引交错 X/Y 原点（direction 为原生 WORD）。54 种组合已写入 `native.py`；
  例如竖排 0/0 为 `(114,30)`，横排 0/0 为 `(400,20)`，竖排 2/8 为 `(20,270)`。
  Ren'Py 原生竖排使用 `(x+width,y)` 为右上锚点；折行读取物理高度。
  SDK 的 TextSegment 不自动继承方向，需要启用 HarfBuzz 及竖排字形，否则
  只有布局被旋转、汉字会侧转。隔离截图已检查字形直立和横竖排切换。
- `0x41c8cb → 0x41f220` 的 tbox 按第二参数调用 `0x41e550/0x41e570`，
  随后按队列条件刷新。隐藏路径 `0x42da47` 也调用 `0x42d9d0` 清页，
  不是只改窗口可见性。0999 在结束时只有 tbox 0 0，没有单独 txcls，
  因而这里必须同时清除页缓冲；`0x41ca48 → 0x41ecd0 → 0x41e590` 是 txcls。
- `0x41c801 → 0x41f890` 的 locmode 读取四表达式，Layer=0 遍历 1..99；
  `0x41e310 → 0x405740` 写对象原点字段。非零第四字段尚未还原，样本全为零。
  `0x408569..0x4085d5` 根据前两字段是否非零，从坐标减去宽/高的整数一半，
  确认水平/垂直中心原点，不是另一款游戏的推测。半像素边界需画面对照。
- `0x41cb25` 的 endscene 只检查回放 WORD `0x4821f8`；正常剧本继续，
  非零退出解释器。当前没有原生鉴赏入口，运行时标志默认为 false。

公共运行时提供已建立的寄存器、媒体和控件机制；没有从其他游戏覆盖层复制
专用行为。普通转场采用公共兼容层，像素和时序一致性未以本 EXE 证明。

## 等待动画与特典版鉴赏资源

- `0x430cb0..0x430d39` 的表是 `[24,18,12,18,16,12]`，以原生
  `3*direction+size` 选择 `grps/waitNN`，不使用其它游戏的 body/grow 三角提示。
  四个 LWG 各有 60 帧，按 `.meta.xml` 中项目顺序播放，保留逐帧原点。
- `0x4191a9` 设置配置指针为 `0x47e588`；`+0x190` 的 WORD 是 50。
  `0x4192b1 → 0x44fc90 → 0x44fca0` 安装 50ms 定时器；
  `0x44b980` 每次增加帧索引、`0x44b9ab` 在末尾归零，非 body/grow 发光动画。
- `0x430dfc → 0x430f60 → 0x455b30` 取得最后字的布局单元矩形。
  `0x430e01` 分支：竖排 wait 位于该单元左下，横排位于右上；不是固定屏幕右下。
  端口使用当前 Ren'Py 已排版字形的单元坐标，ruby 不作为末字。
- 竖排 opening bracket 的 HarfBuzz 墨迹边界会越过完整的 advance，造成
  `『「【` 与下一字重叠。共享原生文本适配层将可容纳的字形 bearing 收回自身
  单元，不改变全角 advance 或列距；24/18/12px 的实际 SDK 字形边界均有回归检查。
- `0x41cee0 → 0x41fb80` 的 folder 指令，Layer=0 在 `0x41fbb1..0x41fbc8`
  循环对象 1..99，不是只写槽 0。0201/0301 的 `folder 0 "grpo_ex"` 和
  `locmode 0 0 0 0` 必须一起生效：缩略图从 grpo_ex 加载，左上原点不能
  继承正篇立绘的中心锚点。已复用 Forest/Khime 的 folder-all 能力，但开启依据
  是本作 EXE。鉴赏入口仍由特典 TSC 执行，不新增一套替代菜单。

## 未确认与下一步

- `0x482a66/0x482a6a/0x482a6c` 是初始化后的配置状态。
  它们位于 `.data` 的 BSS 尾部，没有文件内容；不能用 VA 减基址读出默认值。
- 未实现图像内部模式 3、准确转场、原生记录页外观/分页、完整原图设置/鉴赏菜单，
  原生存档与 CFG 导入。Ren'Py 存读档和持久化不等于原生存档兼容。
- 此模型尚无原生运行日志或像素对照，只以反汇编与真实文件表读取为证据。
